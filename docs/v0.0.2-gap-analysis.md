# v0.0.2 gap analysis and implementation plan — DRAFT

**Status:** planning draft, not an accepted roadmap.
**Source:** `CoreBase & CoreSkills — Unified Blueprint v0.0.2`.
**Baseline:** repository at v0.0.1 (`README.md`, `docs/roadmap.md`, `docs/specs/`).
**Assumption:** the blueprint is the target for the next coordinated release of this repository.

## Implementation status

- **P0 — Decisions: delivered.** ADRs [0005](decisions/0005-identity-model.md)–[0008](decisions/0008-corecenter-distribution.md) settle the identity model, consent boundaries, deployment topology and CoreCenter distribution.
- **P1 — Contracts: delivered.** `@oneorigin/identity`, `@oneorigin/templates`, `@oneorigin/persistence` and the `@oneorigin/api` OpenAPI draft are implemented with conformance tests and JSON Schemas. Shared hashing/base64 primitives moved into `@oneorigin/contracts` without changing existing behavior.
- **P2 — Product integration: delivered.** `@oneorigin/client` provides local identity helpers, the optional `ServiceClient` and verified built-in templates. CoreBase gains a Templates tab and identity/session/consent controls; CoreSkills gains a Templates view and the same optional identity controls. In both products, guest mode stays fully offline and template application still goes through the normal review/save path.
- **P3 — Optional service: delivered.** `apps/service` implements email OTP, sessions, consent lifecycle, template validation and authorized observability endpoints behind interchangeable `PersistenceAdapter` and `EmailSender` interfaces. `@oneorigin/sql` adds the PostgreSQL adapter and schema without a hard `pg` dependency. No product requires the service.
- **P4/P5 — CoreCenter and release hardening: external/open.** CoreCenter lives in the existing `OriginLabs1/CoreCenter` repository and consumes this repository's published contracts (ADR 0008). Android builds, signed artifacts and reproducible-release verification remain tracked there; v0.0.2 release hardening in this repository is still open.

This document originally accompanied the planning pass and contained no runtime code; the phases above were implemented in a later pass.

## 1. Executive summary

v0.0.1 delivered two independent, static, local-first PWAs with shared contracts for capability manifests, permissions, execution lifecycle and portable bundles. v0.0.2 adds a **shared identity / membership / consent / verification foundation**, **optional PostgreSQL persistence behind the same contracts**, a **shared template lifecycle**, and **CoreCenter**, an independently deployable Android observability app.

The largest risks are not features but boundaries:

1. Email OTP must not become a permanent email-based identity provider.
2. Capability grants (user → capability) and observability grants (user → authorized programmer) are different authorizations and must not be conflated.
3. Guest mode must remain fully functional; membership adds capabilities, never a precondition for local use.
4. CoreCenter must consume the same contracts without becoming a runtime dependency of either product.
5. PostgreSQL and edge/local deployments must be interchangeable at the contract level, not just similar in behavior.

Recommended sequencing: **contracts first, optional service second, product integration third, CoreCenter fourth, release hardening last**. Attempting all twelve acceptance criteria in parallel will produce incompatible local models.

## 4. Gap analysis by area

### 4.1 Identity and passwordless authentication

**Gap:** no identity, credential, session or recovery concept. All state is anonymous and local.

**Required work:**

- Shared identity contract: `Identity`, `Credential`, `EmailChallenge`, `Session`, `RecoveryGrant`, `VerificationRecord`.
- Email OTP service with: six-digit code, five-minute expiry, single-use, max five incorrect attempts, hashed storage, rate limiting by email and IP, generic responses that do not disclose account existence, secure session cookies/tokens with rotation and revocation.
- Interchangeable email delivery adapter (`smtp`, `api`, `console`/`memory` for local development and tests).
- Optional, never compulsory. Guest mode must work with the service completely unavailable.

**Design decisions needed:**

- Email is a *verified claim*, not a primary identity key. Use an issuer-independent `identityId` (for example `urn:oneorigin:identity:<sha256>`) derived from a user-held key, with email OTP as one proof mechanism among several. This satisfies "no permanent identity should depend on an email or credential provider."
- Decide whether CoreBase and CoreSkills share one identity service deployment or accept independently operated issuers. Recommendation: **one shared contract, multiple issuers**, with verifier-configured trusted issuers.

### 4.2 Membership, roles and programmer profiles

**Gap:** no membership records, organizations, roles or profiles.

**Required work:**

- `ProgrammerProfile`, `Organization`, `Membership`, `Role`, `Capability` (as an authorization concept, distinct from capability manifests) contracts with ownership, scope, versioning and verification fields.
- Profile visibility preferences; private fields never included in public/observability payloads.
- Delegated administration: scoped, time-bounded, revocable appointments.
- Invitation flow with identity verification before any membership or observability authority is granted.

### 4.3 Consent and programmer observability

**Gap:** grants in v0.0.1 cover capability execution inside one product. The blueprint requires a separate consent chain for a programmer/CoreCenter to observe another user's operational data.

**Required work:**

- `Invitation`, `ConsentGrant`, `ObservabilityGrant` contracts. Invitation must record inviting owner/administrator, verified programmer identity, purpose/application, data categories, permitted operations, duration/expiry and revocation mechanism.
- Explicit states: `invited → identity-verified → scope-disclosed → accepted | declined → active → expired | revoked`. Decline grants no access.
- Server-side enforcement of the initial CoreCenter eligibility list (`sircollins1@protonmail.com`, `nasirusuleiman3786@gmail.com`, plus explicitly authorized appointees), with authorization records — never hard-coded trust from an email string alone. Note: these addresses appear in the blueprint; confirm they are intended to be published in the repository before committing them to source.
- Observability API must return **operational metadata only** by default: health, lifecycle, verification outcome, audit integrity, provenance, diagnostics. User content requires a separate, explicitly disclosed scope.
- Consent history and immediate revocation in the user-facing products and in CoreCenter.

### 4.4 Persistence and deployment models

**Gap:** only browser-local IndexedDB. No SQL persistence, no sync, no shared record format across products.

**Required work:**

- Persistence contracts: `PersistenceAdapter` with local (`IndexedDB`) and SQL (`PostgreSQL`) implementations producing identical validated records. Three supported models: user-controlled edge/local DB, OneOrigin-operated PostgreSQL, independently operated PostgreSQL.
- Append-only event journal / change log with stable event ids, causality metadata and explicit conflict surfacing. Avoid silent last-write-wins merges for authorization and consent records.
- Sync protocol with checkpoint/resume, using the existing audit-chain checkpoint concept.
- Schema migrations with contract version negotiation; v0.0.1 bundles must import into v0.0.2 without data loss.

**Recommendation:** do not introduce a CRDT library for v0.0.2. Consent, membership and audit records need explicit conflict resolution, not automatic convergence.

### 4.5 Shared templates

**Gap:** bundles package skills and workspaces, but there is no `Template`/`TemplateVersion` entity or the discover → preview → select → copy/combine → customize → validate → apply → share lifecycle.

**Required work:**

- `oneorigin.template/v0.0.2` schema: id, version, product (`corebase` | `coreskills`), kind, preview metadata, structured inputs for agents, required capabilities/scopes, compatibility constraints, provenance and signature.
- Product-specific template kinds: workspace definitions, execution environments, policies, project foundations (CoreBase); skills, capability definitions, instructions, workflows (CoreSkills).
- Validation: structure, compatibility, permissions and provenance. Templates are data and starting points; applying a template still goes through normal approval for consequential actions.
- Derivation and publishing: new version records link to source template hashes. Human-and-agent customization must preserve provenance.

### 4.6 CoreCenter (Android)

**Gap:** no Android application, no observability read APIs.

**Required work:**

- New `apps/corecenter/` Kotlin + Jetpack Compose module, independently buildable and distributable.
- Shared contract consumption: generate Kotlin types from JSON Schema/OpenAPI rather than hand-copying TypeScript types.
- Two modules (CoreBase health, CoreSkills health) plus shared consent/revocation UI.
- Clear live / offline / stale indicators. Real-time updates when connected (WebSocket or SSE), with graceful degradation.
- Read-only by design: administration actions require separately scoped, revocable grants.

### 4.7 Verification, recovery and privacy

**Gap:** audit chaining exists for execution, but there is no verification of identity/membership/authorization records, no account recovery, and no profile privacy model.

**Required work:**

- Verifiable record envelope: canonical bytes + content hash + issuer signature + chain inclusion, usable offline from an edge database or exported bundle.
- Recovery: at least one provider-independent mechanism (recovery codes generated locally, plus optional verified alternate channel). Recovery must not silently replace an existing identity key.
- Privacy: field-level visibility classes (`public`, `members`, `self`, `consented`), redaction in logs/telemetry, and tests that assert private fields never cross product or observability boundaries.
- Minimal telemetry, off by default for anything containing content.

### 4.8 Documentation, builds and release

**Gap:** v0.0.1 docs are complete for a static-only release; v0.0.2 adds a service and an Android app.

**Required work:**

- New/updated specs: identity, membership, consent, templates, synchronization, observability API (OpenAPI), recovery.
- ADRs for identity model, deployment topology, consent separation and CoreCenter distribution.
- Reproducible builds for web, service container and signed Android APK/AAB.
- v0.0.2 release artifacts with checksums and migration notes; v0.0.1 artifacts remain available.

## 7. Risks and open questions

1. **Email addresses in the blueprint.** Confirm whether publishing the two initial eligibility addresses in repository docs is intended. Even if published, enforcement must be by verified authorization record, not by address matching.
2. **Issuer trust.** Who can issue verifiable membership records, and how does an offline edge database decide which issuers to trust? Recommendation: user-configured trust anchors with explicit revocation lists.
3. **Scope of "real-time".** Define whether CoreCenter requires a persistent connection or can operate on polled/stale snapshots with clear indicators. Recommendation: snapshots first, streaming as an additive capability.
4. **Native execution.** The blueprint mentions Rust for CoreBase's execution engine. v0.0.1 deliberately excludes real privileged native execution from the browser. Decide whether v0.0.2 includes a native bridge or only defines the contract. Recommendation: contract only; no privileged browser execution.
5. **Android build in CI.** This repository currently has no Android toolchain. Adding one affects CI images, signing key management and release artifacts; decide before P5.
6. **PostgreSQL as a third deployment model.** "Independently operated PostgreSQL" needs a documented operator trust and upgrade model, not only a connection string.
7. **Contract versioning.** v0.0.1 schemas are explicitly unstable. A coordinated v0.0.2 release should still be additive: keep `oneorigin.capability/v0.0.1` and `oneorigin.bundle/v0.0.1` valid; introduce new schema ids for new entities.

If the goal is a smaller first increment, implement P0 + P1 + P2 as **v0.0.2-alpha** and defer the service, templates integration and CoreCenter to v0.0.2-beta — but do not relabel those deferred items as complete.
